# APG79C JavaScript known debt and integration disposition

APG79C exercises the maintainer's explicit authority to accept exactly four
retained APG79B JavaScript qualification limitations as Medium known debt for
provisional integration only. The decision does not accept any Critical or
High finding, semantic defect, normative-source defect, target defect,
whole-file ownership defect, release defect, or rollback defect. It does not
authorize correction of the four limitations.

## Human-accepted qualification boundary

`JS-QD-001` through `JS-QD-004` retain the bounded CommonJS completeness,
process-exception privacy, static process-owner coverage, and root-scalar
mutation limitations. The canonical register records scope, consequence,
safety basis, workaround and stop, owner, repair and refresh conditions, target
impact, maturity effect, and rollback relevance for each item.

The operational restrictions remain mandatory. CommonJS wrapper, loading,
resolution, and execution questions stop with the Node/CommonJS owner.
Harnesses use only APG-owned non-sensitive fixtures. Maintainers manually
review new JavaScript-engine invocation sites and additions to the structured
root-value contract. The four items block stable JavaScript maturity.

The five accepted CSS debt objects remain field-for-field unchanged. The
shared canonical register contains those five objects followed by the four
JavaScript objects. Profile rollback deactivates only that profile's current
entries and preserves the other profile's exact debt set.

## Decision-state evidence

Fresh focused evidence passes the retained 134-test JavaScript selection and
the 104-test known-debt and CSS selection. Exact public/private agreement binds
the nine-entry register and its per-entry identities. Fresh non-author review
found no hidden Critical or High consequence and no hidden semantic, normative
source, target, owner, release, or rollback consequence within the four-item
accepted set.

## Integration preflight

Integration has not opened. Fresh read-only source verification found that the
current official Test262 main identity differs from the identity asserted by
the APG79B terminal operational record and the APG79C assignment baseline.
Test262 remains non-normative rights and corpus evidence and was not used as an
oracle, so the discrepancy has no JavaScript semantic, target, owner, or
execution consequence. It is nevertheless a separate, unaccepted Medium
source-evidence defect and therefore blocks provisional integration under the
authorized stop rule.

ADR 0045 remains Proposed and JavaScript remains
`repair-required-after-apg79b` and unintegrated. Catalog, projection, maturity,
routes, project selection, releases, public and active v0.4.0, and read-only
targets are unchanged. Full integration regression, release reconstruction,
rollback adoption, publication, deployment, target execution, APG80, and other
successor work have not run and are not authorized.

## Terminal checkpoint

The APG79C human-debt decision and its managed report pair preserve the exact
human acceptance. Because the separate Test262
source-identity defect is unaccepted, ordinary product integration gates did
not open. Full integration, release, and rollback gates therefore did not pass
and were not represented as passing.

The terminal disposition is repair-required without rejection or removal. ADR
0045 remains Proposed, JavaScript remains `repair-required-after-apg79b` and
unintegrated, main remains exact APG77D, and APG80 is not recommended. The next
action requires a new human decision.
